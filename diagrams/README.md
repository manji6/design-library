# diagrams — 図解パターン

## 考え方

図解パターンは、描き方ではなく「情報の表現構造」を文章で定義する。狙いは、こういう情報をまとめたいときに、どの図解の型が成り立つかを引けるようにすること。

- パターンは「情報の役割（主体、状態、遷移など）」と「視覚表現（ボックス、矢印、吹き出し、塗り）」の対応だけを持つ。
- 色、寸法、書体はデザイン側（designs/）の領分で、パターンは色を指定しない。
- 共通語彙は vocabulary.md、選択は index.md、記述の型は _template.md。

## エージェントの利用手順

1. **要点を1文にする**: 素材から「読者が図を見て持ち帰る答え」を1文で書く。言えなければ図にしない。
2. **系統を判定する**: index.md の振り分け質問で5系統のどれかに絞る。
3. **候補を2〜3に絞る**: index.md の「伝えたいこと」と「手がかり」から候補を選び、各パターンの「近いパターンとの見分け」で1つに決める。
4. **役割を埋める**: パターンの「分解の問い」に答えて必須の役割を埋める。埋まらなければそのパターンは不適なので、3に戻る。この戻りが品質の要。
5. **出口**: 候補がすべて不適、または name-only しか当たらないときは、無理に当てはめない。(a) 要点が文章や表で足りるなら図にしない。(b) 図にするなら、index の該当行の「問い・手がかり」だけで分解メモを作り、判定欄に「name-only: <id> を索引情報のみで使用」と書く。(b) は適用ではなく例外扱いであり、作業の報告にも「name-only: <id> を索引情報のみで使用（不足）」と明記する。近い defined / example のパターンで黙って代用してはならない。
6. **粒度と個数を確認する**: ラベルの粒度がそろっているか、役割表の目安を超えていないか。超えていれば図を分けるか、まとめる。
7. **修飾を決める**: 強調は原則1つで、理由を1文で書けるものだけ。注釈は特筆事項だけ。
8. **分解メモを出す**: 実例と同じ書式（要旨／判定／分解／略図／判断メモ）で出す。人間が確認できる中間成果物。
9. **描画する**: 対象デザインの DESIGN.md の図解部品表に従い、役割ごとに決められたトークンと手がかりを使う。
10. **成立チェック**: 色と塗りを外しても、1の答えが読めるかを確認する。強調は色以外の手がかりで残ること。

## サンプルからの起こし方

本人が作ったサンプルと説明を受け取ったら、不足分を「分解の問い」で聞き返して分解メモを作り、_template.md の12見出しに整形してパターン化する。本人が意図（何を伝えたいか、強調の理由）を確認してから登録する。
